# HTTP API

Все маршруты имеют префикс `/api/v1`. Тела `POST` — JSON; неизвестные поля
отклоняются. Коэффициенты и табличные значения времени в запросе передаются
конечными десятичными строками (`"0.125"`), а результаты также могут содержать
точную дробь (`"4/3"`). Ответ ошибки имеет форму
`{"error":"validation_error","message":"…","details":{…}}`.

## Модель

Узел с параметрической функцией задаётся объектом:

```json
{"id":"A","name":"Узел A","a":"0","b":"1","kind":"linear"}
```

`kind` — `linear` для `T(k)=a+b*k` или `quadratic` для `T(k)=a+b*k²`.
Для этих видов требуется `a >= 0`, `b > 0`.

Произвольную фиксированную зависимость можно передать таблицей:

```json
{"id":"A","name":"Узел A","kind":"table","table_values":["1","2","5","9"]}
```

Для `kind: "table"` поле `table_values` содержит ровно `players` значений
`T(1), …, T(n)`. Каждое значение должно быть неотрицательным и не меньше
предыдущего. Параметры `a` и `b` для табличного вида не используются. Во всех
трёх вариантах алгоритмы обращаются к единому `T_j(k)`: потенциал Розенталя,
поиск выгодных переходов, проверка равновесия и оптимизация не зависят от
способа задания значений.

Идентификаторы должны быть уникальными. Поддерживается от 1 до 500 заданий и
от 1 до 40 узлов. ID ограничен 64 байтами, имя — 120 байтами, а каноническая
точная запись одного входного значения — 256 символами. API не исполняет
формулы, переданные пользователем.

## Основные маршруты

| Метод и маршрут | Назначение |
| --- | --- |
| `GET /health` | Версия и состояние API. |
| `GET /presets` | Три проверочных сценария A/B/C. |
| `GET /presentation` | Подготовленные проверенные данные для полного и краткого read-only показа защиты. |
| `POST /preview` | Таблица значений `T_j(k)` для редактора модели. |
| `POST /simulations` | Серверный поиск строгих улучшений и сохранение трассы. |
| `GET /simulations/{id}` | Сохранённый запуск. |
| `POST /optimize` | Точный оптимум по векторам загрузок и PoA в пределах лимита. |
| `POST /experiments` | Воспроизводимая серия запусков. |
| `GET /experiments` | История серий. |
| `GET`, `DELETE /experiments/{id}` | Детали или удаление серии. |
| `GET /experiments/{id}/export?format=csv\|json` | Полный экспорт серии и её запусков. |

## Подготовленная презентация защиты

Веб-маршрут `/presentation` предоставляет два read-only режима. У них общий
источник данных `GET /presentation`, но разные сценарии показа:

| Режим | Слайды | Назначение |
| --- | --- | --- |
| Полный показ | Все 10: модель, исследовательские вопросы, причина завершения динамики, опыты А/Б/В, сложный случай, серия и выводы. | Подготовка, обсуждение и ответы на вопросы. |
| Краткий показ для защиты | `5 → 7 → 8 → 9` | Защита продолжительностью до 3 минут. |

Краткий режим начинается со слайда 5 и переходит только к следующему слайду
этой фиксированной последовательности, а не ко всем десяти слайдам. Он не
принимает параметры, не меняет модель и не запускает вычисление: во время
показа доступны только навигация и полноэкранный режим. Поэтому на странице
нет формы, кнопки запуска и POST-запроса.

На слайде 3 используются «исследовательские вопросы», а не гипотезы:
завершение строго улучшающей динамики — известное теоретическое свойство
потенциальной игры, которое программа иллюстрирует. Слайды 8 и 9 показывают
результаты, рассчитанные программой; серия на слайде 9 меняет только число
задач `n=8,16,32` при фиксированных функциях четырёх узлов, начальном
распределении и правиле `first_improvement`.

Формулы в слайдах используют единые обозначения: `T_j(k)`, `t_i(s)`,
`n_j(s)`, `Φ(s)`, `S(s)` и `K_найд`. Внутренние идентификаторы движка
отделены от математических обозначений на слайдах.

## Маршрут `GET /presentation`

`GET /presentation` является источником подготовленных слайдов. Пакет данных
один раз формируется игровым ядром при инициализации API: для каждого сценария
выполняются поиск равновесия, проверка Нэша и точная оптимизация. Затем
обработчик только отдаёт неизменяемый снимок — при открытии и перелистывании
слайдов вычисления не запускаются и SQLite не используется.

```json
{
  "linear_preview": [
    {"load": 1, "a": "1", "b": "2"},
    {"load": 2, "a": "2", "b": "4"},
    {"load": 3, "a": "3", "b": "6"},
    {"load": 4, "a": "4", "b": "8"}
  ],
  "equilibrium_comparison": [
    {"profile": "(A,A)", "total_time": "4"},
    {"profile": "(A,B)", "total_time": "3"}
  ],
  "potential_trace": [
    {"step": 0, "potential": "10"},
    {"step": 1, "potential": "7.5"},
    {"step": 2, "potential": "6.5"}
  ],
  "scenarios": [
    {
      "id": "A",
      "players": 2,
      "initial": {"assignment": ["B", "B"], "potential": "6", "total_time": "8"},
      "trace": [{"step": 1, "potential": "3", "total_time": "3"}],
      "final": {"assignment": ["A", "B"], "potential": "3", "total_time": "3"},
      "nash": {"is_equilibrium": true},
      "optimum": {"total_time": "3"},
      "k_run": "1",
      "poa": "4/3"
    }
  ],
  "complex_scenario": {"players": 8, "k_run": "152/143", "poa": "152/143"},
  "series": [{"players": 4, "nodes": 2, "steps": 2, "k_run": "1"}],
  "scaling_setup": {
    "initial_node_id": "У₁",
    "algorithm": "first_improvement",
    "nodes": ["... четыре линейные или квадратичные функции ..."]
  },
  "scaling_series": [
    {"n": 8, "m": 4, "h": 15, "equilibrium_status": "equilibrium", "s_equilibrium": "11.2", "s_optimum": "10.48", "k_run": "140/131", "exact_status": "exact"}
  ]
}
```

`scenarios` содержит подготовленные сценарии A/B/C. Каждый объект включает
`nodes`, `initial`, `trace`, `final`, `nash`, `optimum`, `k_run`, `poa` и
`worst_equilibrium`; все десятичные величины и точные дроби передаются строками.
`complex_scenario` имеет ту же схему. `series` содержит точки фиксированной
сетки с полями `players`, `nodes`, `steps`, `k_run`, `total_time_ne` и
`total_time_opt`. `scaling_setup` и `scaling_series` — отдельная
контролируемая серия для слайда 9. В `scaling_series` поле `h` — число
строго выгодных переходов; `s_equilibrium` появляется только после
подтверждённого равновесия, а `s_optimum` и `k_run` — только когда точная
оптимизация завершена. Статусы `equilibrium_status` и `exact_status`
позволяют интерфейсу честно показать «не вычислен», а не подменять результат.

## Симуляция

Пример запроса `POST /simulations`:

```json
{
  "players": 2,
  "nodes": [
    {"id":"A","name":"Узел A","a":"0","b":"1","kind":"linear"},
    {"id":"B","name":"Узел B","a":"0","b":"2","kind":"linear"}
  ],
  "initial_assignment": ["B", "B"],
  "algorithm": "first_improvement",
  "max_steps": 100,
  "seed": 42
}
```

`algorithm` — `first_improvement` или `best_response`; `max_steps` находится
в диапазоне от 1 до 500. В ответе создаётся
`SimulationResponse`: `initial`, `trace`, `final`, `nash_check`, `status` и
`message`. Каждый элемент `trace` содержит игрока, переход, `previous`,
`next`, `delta`, `potential`, `total_time` и полный серверный `summary` после
шага (распределение, нагрузки, `F`, `S`). Это позволяет клиенту только
отображать данные, не пересчитывая игру.

Статус `equilibrium` выдаётся только после завершения динамики без улучшений
и независимой проверки Нэша. `step_limit` и `cancelled` не являются
равновесием даже если финальная независимая проверка уже не нашла улучшения.

## Оптимизация и PoA

`POST /optimize` принимает `players`, `nodes`, `max_states` и, необязательно,
`initial_assignment`, `algorithm`, `max_steps`. При наличии начального
распределения ответ также может содержать `equilibrium` и `k_run`; они
появляются только для запуска со статусом `equilibrium`.

Ответ включает:

```json
{
  "optimum": {"status":"exact","total_time":"3","loads":[...]},
  "equilibrium": {"total_time":"3","loads":[...]},
  "k_run": "1",
  "poa": {
    "status":"exact",
    "value":"4/3",
    "worst_equilibrium":{"total_time":"4","loads":[...]}
  }
}
```

Для `optimum` и `poa` статус — `exact`, `not_computed`, `cancelled` или
`error`. Если число векторов загрузок превышает предел или расчёт отменён,
сервер не выдаёт частичный результат за точный и не подменяет PoA значением
`k_run`.

## Эксперименты

`POST /experiments` принимает конечную декартову сетку:

```json
{
  "players":{"from":2,"to":10,"step":2},
  "nodes":{"from":2,"to":4,"step":1},
  "a":{"from":"0","to":"0","step":"1"},
  "b":{"from":"1","to":"3","step":"1"},
  "algorithm":"first_improvement",
  "seed":7,
  "max_steps":100
}
```

Ответ содержит идентификатор, конфигурацию и `points`. У точки есть параметры
сетки, число шагов, статусы и (только когда они действительно рассчитаны)
`total_time_ne`, `total_time_opt` и `k_run`. Пределы сетки, размера
сохраняемых трасс, состояний точного перебора и времени вычисления ограничены
сервером. Декартова сетка содержит не более 10 000 запусков; лимит объёма
сохраняемых трасс применяется отдельно.
