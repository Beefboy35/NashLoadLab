# Nash Load Lab

Локальное исследовательское приложение для конечной атомарной игры с
перегрузкой: задания выбирают один из вычислительных узлов, а сервер находит
равновесие Нэша, точный социальный оптимум и (когда полный перебор укладывается
в лимит) цену анархии.

Все вычисления выполняются на Go-сервере. Интерфейс на React показывает только
полученные трассы и результаты: потенциальную функцию Розенталя `Φ`, суммарное
время `S`, проверку равновесия и воспроизводимые серии опытов. Значения
коэффициентов и результатов передаются как десятичные строки, чтобы не терять
точность при обмене с браузером.

## Быстрый запуск через Docker

Нужны Docker Engine и Docker Compose. Из корня проекта:

```powershell
docker-compose up --build
```

После готовности контейнеров откройте `http://localhost:5173`. Для защиты
курсовой доступна подготовленная презентация:
`http://localhost:5173/presentation`. На странице есть полный и краткий
режимы; оба показывают заранее подготовленные серверным ядром сценарии и не
запускают расчёт во время выступления. API доступен по
`http://localhost:8080/api/v1/health`, а SQLite-данные хранятся в именованном
томе Docker `nash_load_data` и переживают перезапуск контейнеров.

Остановить приложение:

```powershell
docker-compose down
```

Чтобы удалить также сохранённые исследования, выполните
`docker-compose down -v`.

## Локальный запуск без Docker

Требуются Go 1.22+ и Node.js 20+.

```powershell
cd frontend
npm install
cd ..\backend
go mod download
cd ..
.\scripts\dev.ps1
```

Скрипт запускает API на `http://localhost:8080` и Vite на адресе, который
покажет Vite (обычно `http://localhost:5173`). Прокси Vite направляет `/api` к
Go-серверу. База SQLite создаётся в `backend/data/nash-load-lab.db`.

На системах с `make` доступны также цели `make dev`, `make test` и `make build`.

## Презентация защиты

Маршрут `/presentation` содержит два подготовленных read-only режима без
ручного ввода и запуска расчётов во время выступления.

| Режим | Назначение | Содержание |
| --- | --- | --- |
| Полный показ | Подготовка, обсуждение с научным руководителем и ответы на вопросы. | Все 10 слайдов: модель, исследовательские вопросы, объяснение потенциала, опыты А/Б/В, сложный случай, серия и выводы. |
| Краткий показ для защиты | Выступление до 3 минут. | Только ключевая последовательность `5 → 7 → 8 → 9`. |

Краткий показ построен на готовой последовательности экранов и остаётся
read-only: он не принимает параметры, не изменяет сценарии и не отправляет
POST-запросов. Рекомендуемый темп выступления:

| Время | Слайд | Акцент |
| --- | --- | --- |
| 0:00–0:35 | 5. Опыт А | Подстановка чисел в строго выгодный переход и проверка равновесия. |
| 0:35–1:05 | 7. Опыт В | Явный контрпример: равновесие может не совпадать с оптимумом. |
| 1:05–1:45 | 8. Сложный случай | Восемь задач, четыре неоднородных узла, траектория и точный оптимум. |
| 1:45–2:40 | 9. Серия опытов | Меняется только число задач; графики `H(n)` и `K_найд(n)`. |

Экран получает один read-only ответ `GET /presentation`. Его значения
подготовлены тем же игровым ядром, что и обычные симуляции и оптимизация, не
записываются в SQLite и не требуют пользовательских POST-запросов. В формулах
презентации используются единые обозначения: `T_j(k)`, `t_i(s)`, `n_j(s)`,
`Φ(s)`, `S(s)` и `K_найд`. На слайде 9 есть заранее рассчитанная
контролируемая серия `n=8 → 16 → 32`: фиксированы четыре формульные функции,
начальное распределение и правило переходов, а конфигурация переключается
одной кнопкой.

В обоих режимах навигация доступна кнопками и клавишами `←`/`→`; клавиши
`Home` и `End` переходят к началу и концу выбранного показа, есть
полноэкранный режим.

## HTTP API

Полные схемы запросов и ответов: [docs/API.md](docs/API.md).

Все маршруты имеют префикс `/api/v1`:

- `GET /health`, `GET /presets`, `GET /presentation`;
- `POST /preview` — серверная таблица `T_j(k)` для редактора модели;
- `POST /simulations`, `GET /simulations/{id}`;
- `POST /optimize`;
- `POST /experiments`, `GET /experiments`, `GET` и `DELETE /experiments/{id}`;
- `GET /experiments/{id}/export?format=csv|json`.

Ошибки возвращаются JSON-объектом с полями `error`, `message` и при наличии
`details`. Сервер ограничивает размер входных данных, число шагов и число
состояний полного перебора; достижение лимита не выдаётся за равновесие или
точный результат.

## Математическая модель

Для узла `j` время можно задать линейной функцией
`T_j(k)=a_j+b_j·k`, квадратичной `T_j(k)=a_j+b_j·k²` (где `a_j≥0`, `b_j>0`)
или таблицей точных значений `T_j(1), …, T_j(n)`. Для табличного режима
значения должны быть неотрицательными и неубывающими. Выгоден только строгий
переход, для которого целевое время с учётом переходящего задания меньше
текущего. Потенциал `Φ=Σ_j Σ_{q=1}^{n_j}T_j(q)` и суммарное время
`S=Σ_j n_jT_j(n_j)` — разные величины. Оптимум ищется по векторам целочисленных
загрузок, а не по всем именованным профилям. Поэтому переходы, проверка
равновесия, потенциал и оптимизация одинаково работают для всех трёх способов
задания `T_j`. `K` характеризует только найденное равновесие; `PoA`
публикуется лишь после полного перебора всех равновесий.

## Ограничения первой версии

Модель предполагает одинаковые задания, один выбранный узел на задание и
условные единицы времени. Она не описывает сетевую миграцию, реальные метрики
задержек, задания разного веса или коалиционные переходы.
